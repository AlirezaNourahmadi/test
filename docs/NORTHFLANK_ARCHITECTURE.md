# Northflank Architecture

## Scope

This document applies only to the `northflank` branch. The Railway-compatible
`main` branch is intentionally unchanged.

## Runtime layout

The Northflank deployment runs one container with two cooperating processes:

1. FastAPI panel on internal port `8000`.
2. Official Xray Core `26.3.27` on internal port `10000`.

Xray also exposes a private management API on `127.0.0.1:10085`. It is not a
Northflank port and cannot be reached from the public internet.

Northflank terminates TLS for both public endpoints:

| Purpose | Internal port | Public endpoint |
|---|---:|---|
| Panel/API/subscriptions | 8000 | `https://garibar--test--tvbmvy4f8p8m.code.run` |
| VLESS over WebSocket | 10000 | `https://xray--test--tvbmvy4f8p8m.code.run` |

The VLESS endpoint uses WebSocket path `/ws`. TLS and SNI use the Xray public
hostname. New links generated by the panel therefore use the following shape:

```text
vless://UUID@xray--test--tvbmvy4f8p8m.code.run:443
  ?encryption=none
  &security=tls
  &type=ws
  &host=xray--test--tvbmvy4f8p8m.code.run
  &path=/ws
  &sni=xray--test--tvbmvy4f8p8m.code.run
  &fp=chrome
  &alpn=http/1.1
```

## Control plane and data plane

FastAPI is the control plane. It owns authentication, link metadata,
subscriptions, expiry, traffic quotas, and the dashboard.

Xray Core is the data plane. It parses VLESS, handles WebSocket framing, DNS,
TCP, UDP, outbound connections, and per-user traffic counters. The custom
Python relay remains in the repository for Railway compatibility, but links
created in Northflank mode do not use it.

The Northflank container resolves outbound domains with `UseIPv4`. Runtime
inspection confirmed that the pod can resolve IPv6 addresses but has no working
IPv6 route (`connect_ex=99`). Allowing Xray's generic `UseIP` selection could
therefore choose an unreachable IPv6 address and make otherwise valid sessions
fail intermittently.

The panel starts Xray at application startup with every allowed UUID. Later
create, enable, disable, reset, expire, and delete operations are sent to the
private Xray HandlerService. If a dynamic update fails, the supervisor restarts
Xray from the desired complete user set instead of leaving partial state.

## Persistence

Panel state is stored atomically in `/data/x4g_state.json`. The session/password
secret is stored in `/data/x4g_secret.key` unless `SECRET_KEY` is explicitly
provided. The container runs as non-root UID/GID `10001`, and the image declares
ownership of `/data` for that identity.

The current no-cost deployment intentionally has no Northflank volume. Its
`PERSISTENCE_MODE` is `ephemeral`: state survives application-process restarts
inside the same container, but it is lost when Northflank replaces or redeploys
the container. `/health` reports both write availability and durability so a
writable container filesystem cannot be mistaken for persistent storage.

Durable state remains an optional future change. Attach one read/write volume
to `/data`, keep the service at one replica, and set
`PERSISTENCE_MODE=volume`. No code or PostgreSQL migration is required.

PostgreSQL is not needed for this deployment. There is one panel replica, the
state is small, writes are serialized, and an atomic JSON file is enough. A
PostgreSQL service would add credentials, migrations, network dependencies, and
backup operations without solving an actual concurrency problem. A database
becomes justified if the panel is changed to multiple replicas or needs
relational reporting.

Using a PostgreSQL instance on a laptop is specifically unsuitable for this
production service because availability would depend on the laptop, home
network, public routing, and firewall state.

## Feature decisions

The Northflank create flow intentionally offers official VLESS/WebSocket only.
It fixes ALPN to `http/1.1` and public port to `443` because those values match
the Northflank HTTP/WebSocket ingress.

Traffic quotas and expiry remain enforced. The panel polls Xray's user traffic
counters every 15 seconds, persists positive deltas, and removes a user from
Xray when the quota or expiry condition is reached.

Per-user speed and simultaneous-IP limits from the Python relay are not exposed
in this branch. Xray does not provide equivalent per-user enforcement through
the selected HandlerService/StatsService design, and displaying controls that
do nothing would be misleading.

## Failure behavior

- Invalid Xray configuration stops application startup and prevents a false
  healthy deployment.
- A dead Xray process is reported by `/health` as `degraded` with HTTP 503.
- A non-writable `/data` path is reported by `/health` as `degraded` with HTTP
  503.
- Ephemeral storage is reported as `durable: false` but does not degrade the
  service because it is the deliberate current operating mode.
- Outbound domain resolution defaults to IPv4 because this Northflank runtime
  does not have a usable IPv6 route.
- Failed dynamic user synchronization triggers a full Xray restart with the
  desired users.
- State writes use a temporary file followed by an atomic rename.

Northflank has an HTTP readiness probe on panel port `8000` and `/health` with
a 10-second initial delay, 15-second interval, 5-second timeout, and three-fail
threshold. New containers receive traffic only after both storage and Xray are
ready.

## Security boundaries

- Xray's management API listens only on loopback.
- TLS is terminated by Northflank on the public HTTP ports.
- Only active, non-expired, under-quota UUIDs are installed in Xray.
- No panel secret is committed to Git.
- The container runs as a dedicated non-root user.
